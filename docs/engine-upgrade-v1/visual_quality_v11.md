## 3) بهینه‌سازی موبایل — و معمای 6095ms

| پروفایل شبکه (کش سرد) | SPZ ready (fetch+decode) | اولین فریم | نتیجه |
|---|---|---|---|
| localhost (بدون شبکه) | **475–540 ms** | 91–233 ms | زمان دیکدِ موتور |
| **fast3g 1.6Mbps/150ms** | **6,108 ms** | 5,178 ms | **= عدد HUD مالک (6095ms) با اختلاف 0.2%** |
| 1.5Mbps/150ms | 6,548 ms | 5,490 ms | پهنای‌باندِ مؤثر مالک ≈ 1.5Mbps |
| slow3g 0.5Mbps/400ms | 18,447 ms | 16,078 ms | 3G ضعیف |

**علت اختلاف 6095 ↔ 338–934ms:** هر دو عددِ قبلی آزمایشگاه localhost بودند (شبکه صفر). عدد HUD روی آیفون = زمان **انتقال 1.09MB از GitHub Pages روی لینک موبایل** (~1.5Mbps) + ~0.5s دیکد. رگرسیون موتور **نیست**. (نکتهٔ جانبی: در همان بارگذاری، spark.module.min.js ‏2.86MB و پانوی 4K ‏0.95MB هم رقابت پهنای‌باند دارند — resource-timing ثبت شد.)

- **FPS/p95 (نسبیِ SwiftShader، مطلقِ آیفون نیست):** idle 16–57fps، walk 13–23fps در نرم‌افزار؛ **جریمهٔ فاصله صفر** (FPS مستقل از dist). اعداد مطلق واقعی: `?autotest=1` روی آیفون مالک (باتریِ درون‌صفحه‌ای: 10s سکون + باتری راه‌رفتن ۴جهته + JSON قابل‌کپی با resource-timing واقعی شبکهٔ شما).
- **حافظه:** JS heap در Chromium-emulation: **12.8–16.3 MB**؛ Safari `performance.memory` ندارد (n/a روی آیفون — در autotest ثبت می‌شود).
- **کیفیت در حرکت/توقف:** توقف = پانوی 4K تیز (وضوح 1.03× ایده‌آل)؛ حرکت = تک‌تصویرِ تمیز V1.1 (blur-only) — VLM: «acceptable-transient».
